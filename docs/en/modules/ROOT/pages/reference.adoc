== Build-time code generation

* **`foy-processor`** is a build-time annotation processor with a single requirement, `java.compiler`. It generates `X$$FoyComponent` for `@WebServlet`, `@WebFilter`, `@WebListener`, for unannotated `Servlet` / `Filter` / listener classes and for `ServletContainerInitializer` (with its `@HandlesTypes`), carries `@MultipartConfig`, `@ServletSecurity`, `@DeclareRoles` and `@RunAs` metadata, and writes `META-INF/services/io.vidocq.foy.spi.gen.WebComponent` plus `META-INF/foy/class-index.list`. Spec misuse is a compile error; a class that cannot be generated is reported as a note.
* **`FoyWebExtension`** (in `foy-cdi-vauban`) is a CDI Build Compatible Extension. It runs inside `vauban-processor`, which is itself **build-time only**: unscoped web components become `@Dependent`, duplicate servlet or filter names fail the build, and a synthetic `@Singleton` `io.vidocq.foy.spi.cdi.CdiWebComponents` bean lists the components for `WebAppDiscovery`, which merges the beans of the application and of every library archive. A web-annotated `Servlet`, `Filter` or `EventListener` bean missing from every index (its archive was built without `foy-cdi-vauban` on the processor path) is still discovered, with one `WARNING` per class.
* See xref:internals.adoc#component-resolution-tiers[Component resolution tiers] for the runtime side and xref:usage.adoc#build-time-code-generation[Usage] for the setup.

| `Builder.confidentialPort(int port)` [.tag-new]#NEW#

| `Builder.rotateSessionIdOnLogin(boolean rotate)` [.tag-new]#NEW#

| `Mounted.handler()`

| `Mounted.servletContext()`
| The container's `VidocqServletContext` — useful for observability.

| `Mounted.close()`

[#security]
== Security [.tag-new]#NEW#

=== `IdentityStore` contract

`IdentityStore.validate(username, password)` returns the caller's `Identity` (principal and application roles) or `Optional.empty()`. An implementation must:

* compare secrets in constant time (`MessageDigest.isEqual`) and spend the same work on an unknown user as on a wrong password;
* never log, keep or echo the password; Foy wipes the `char[]` as soon as `validate` returns;
* return `Optional.empty()` on any refusal. Foy treats an exception or a `null` result as a refusal, and logs only the exception class of a `RuntimeException`;
* never put the user name or the password in an exception message.

The roles are application role names, used as they are by the constraints and by `isUserInRole` (after the servlet's `security-role-ref`s). Foy maps no group.

=== The in-memory store

`FoyChappeBoot.Builder.user(...)` fills Foy's in-memory store. Each password is kept only as a salted SHA-256 digest (16 random bytes of salt); validation compares digests with `MessageDigest.isEqual` and digests a decoy for an unknown user, so the response time does not tell which user names exist. It is meant for a fixed set of users declared by the embedder, **not as a password database**: a persistent or shared user base plugs its own `IdentityStore`, with a slow hash (PBKDF2, Argon2) if it stores hashes.

=== Mechanisms and behaviour

[cols="1,3",options="header"]
|===
| Topic | Behaviour

| `auth-method`
| `BASIC` (also when there is no `login-config` or no `auth-method`) and `FORM`. `CLIENT-CERT` is deferred; `DIGEST` and any other value are not supported. An unsupported method is logged at deploy and its protected resources answer `403`.

| Realm
| `login-config/realm-name`, or `Restricted` by default, in `WWW-Authenticate: Basic realm="..."`.

| FORM challenge
| The request is forwarded to `form-login-page` (the browser keeps its URL). Only a `GET` or `HEAD` target is saved, server-side in the session, rebuilt from the request URI and query; a protected `POST` is not replayed. A FORM `login-config` without a login page answers `403`. The login and error pages are sent with `Cache-Control: no-store` and `Pragma: no-cache`, so no cache keeps the login page at the protected URL; a page that sets those headers itself, or calls `reset()`, replaces them.

| `j_security_check`
| `POST` only (`405` with `Allow: POST` otherwise), on any path ending in `/j_security_check`. On success: identity bound, session id rotated, identity kept in the session, `302` to the saved target or the context root. The redirect carries the session id only when the client sent it in the URL. On failure: forward to `form-error-page`, or `403` without one. Over plain HTTP it is accepted unless a CONFIDENTIAL constraint covers its path.

| Session id rotation
| Every successful login (FORM action or `login()`) changes the id of an existing session, unless `rotateSessionIdOnLogin(false)`.

| `login()`
| Validates against the store and sets the configured mechanism as auth type. Under FORM the identity is kept in the session, which is created if needed; under BASIC it lasts for the request. A mechanism without password login (CLIENT-CERT, unsupported ones) throws `ServletException`.

| `logout()`
| Clears the identity of the request and of the session. The session and its attributes stay.

| `authenticate()`
| `true` when the request has an identity; otherwise the mechanism's challenge (`401` BASIC, login page FORM) and `false`.

| CONFIDENTIAL / INTEGRAL
| Both mean HTTPS required. A plain request gets `403`, or a `302` to `https://<Host>:<confidentialPort><uri>?<query>` when `confidentialPort` is set (no port in the URL for 443). The redirect host comes from the client's `Host` header; an IPv6 literal or an invalid Host, and a raw request URI or query holding a non-ASCII, space or control character, get `403` instead. A `POST` body is not carried over the redirect.

| Reverse proxy
| Behind a TLS-terminating proxy, `isSecure()` is `false`, so a CONFIDENTIAL constraint redirects again and again. Terminate TLS in Chappe, or do not declare the transport guarantee on such a deployment.

| Denials
| `401` and `403` go through the `<error-page>` handling, like `sendError`.

| Unconfigured context
| A context built outside the deployer refuses every request (`403`): security fails closed. Its first refused request logs one `WARNING` saying so.

| Roles
| `*` in an `auth-constraint` stands for every declared role; `**` for any authenticated user unless a role `**` is declared. No group mapping.

| `run-as`
| `<run-as>` and `@RunAs` are reported by `ServletRegistration.getRunAsRole()` but not propagated: there is no EJB container.

| `setServletSecurity`
| Returns the url-patterns already constrained by the descriptor (left unchanged); throws `IllegalStateException` once the context is initialised.
|===

== `web.xml` and `web-fragment.xml` coverage

`WebXmlParser` reads the Servlet 6.1 `web-app_6_1` schema and the `web-fragment` variant. The root element is checked, DOCTYPE is disallowed, and a parse error names the offending element. Descriptors are merged with the annotated components per Servlet 6.1 §8.2.3: `web.xml` wins on a same-name conflict, a conflict between two fragments fails the deployment, a `url-pattern` claimed by two components fails (§12.2), and `metadata-complete="true"` ignores annotations and fragments. `<init-param>` duplicates keep the first value; `<async-supported>` is tri-state (unset, true, false); `<session-config>/<cookie-config>` merges per sub-element.

[cols="2,1,3",options="header"]
|===
| Element | Status | Notes

| `<display-name>`, `<context-param>`, `<listener>`, `<error-page>`, `<locale-encoding-mapping-list>`
| applied
|

| `<servlet>`, `<servlet-mapping>` (`init-param`, `load-on-startup`, `async-supported`, `enabled`, `multipart-config`)
| applied
| `<enabled>false</enabled>` leaves the servlet unserved; `web.xml` multipart-config wins over `@MultipartConfig`

| `<servlet>` with `<jsp-file>`
| skipped
| no JSP engine: logged at `WARNING`, the rest of the deployment proceeds

| `<run-as>`
| parsed
| not applied

| `<filter>`, `<filter-mapping>` (`dispatcher`, `servlet-name`, `url-pattern`)
| applied
| `async-supported` is tri-state

| `<session-config>` (`session-timeout`, `cookie-config`, `tracking-mode`)
| applied
| the session cookie follows `SessionCookieConfig`; tracking modes reach `getEffectiveSessionTrackingModes()` and govern input as well as output; a `session-timeout` of zero or less never expires

| `<mime-mapping>`
| applied
| feeds `ServletContext.getMimeType`

| `<request-character-encoding>`, `<response-character-encoding>`
| applied
| `ServletContext` getters return `null` when unset

| `<default-context-path>`
| applied
| used when the builder sets no context path; web.xml only — a fragment's is ignored with a warning

| `<welcome-file-list>`
| applied
| consumed by the container default servlet: static file first, then servlet; see xref:usage.adoc#welcome-files[Welcome files]

| `<deny-uncovered-http-methods>`
| enforced
| an uncovered method at a constrained pattern answers `403`; without it, it is open and reported at deploy

| `<security-constraint>`, `<login-config>`, `<security-role>`
| enforced
| per url-pattern, merged with `@ServletSecurity` (the descriptor wins on an exact pattern); `auth-method` BASIC or FORM, any other fails closed; see <<security>>

| `<security-role-ref>`, `<run-as>`
| applied
| `isUserInRole` follows the role-ref of the executing servlet; `run-as` is reported by `getRunAsRole()` only

| `<name>`, `<ordering>`, `<absolute-ordering>`
| applied
| fragment name and §8.2.2 ordering

| `<jsp-config>`, `<resource-ref>`, `<env-entry>` and the other Jakarta EE environment elements
| ignored
| no JSP engine and no naming environment in Foy
|===

The `version` and `metadata-complete` attributes of `<web-app>` and `<web-fragment>` are honoured. A DOCTYPE (Servlet 2.2 and 2.3 descriptors) is accepted without being resolved: the public id sets the version, a version before 2.5 implies `metadata-complete`, and an entity reference is rejected (see xref:usage.adoc#legacy-deployment-descriptors[Legacy deployment descriptors]).

== `HttpServletMapping`

`HttpServletRequest.getHttpServletMapping()` is implemented for every dispatch type; `getMatchValue()`, `getPattern()`, `getServletName()` and `getMappingMatch()` follow Servlet 6.1 §12.2:

[cols="2,2,2,3",options="header"]
|===
| Request | `MappingMatch` | `getPattern()` | `getMatchValue()`

| `/a/b` with servlet `/a/b`
| `EXACT`
| `/a/b`
| `a/b`

| `/a/b/c` with servlet `/a/*`
| `PATH`
| `/a/*`
| `b/c`

| `/x/y.ts` with servlet `*.ts`
| `EXTENSION`
| `*.ts`
| `x/y`

| `/` with servlet `""`
| `CONTEXT_ROOT`
| `""`
| `""`

| any other path, container default servlet or application `/`
| `DEFAULT`
| `/`
| `""`
|===

On a forward the mapping is that of the target; `jakarta.servlet.forward.mapping` keeps the mapping of the original request, and `jakarta.servlet.include.mapping` the one of the included target. The mapping of a nested forward stays the original one. A named dispatch sets no mapping attribute.

== Session configuration

[cols="2,3",options="header"]
|===
| Setting | Behaviour

| Timeout
| `<session-timeout>` (minutes), `ServletContext.setSessionTimeout` (also from a `ServletContainerInitializer`) or `FoyChappeBoot.Builder.sessionTimeoutSeconds`; zero or less never expires. A virtual-thread reaper runs every `min(60 s, max(1 s, timeout / 2))` and fires `sessionDestroyed`; any request carrying a session id accesses (and so extends) the session.

| `getLastAccessedTime()`
| Time of the previous request.

| Tracking modes
| Default `{COOKIE, URL}`; `SSL` only when configured. Enforced on input: the cookie is read only with `COOKIE`, `;jsessionid` only with `URL` and when no cookie is sent; the cookie wins when both are present.

| `changeSessionId()`
| Keeps the attributes, fires `HttpSessionIdListener.sessionIdChanged`, sends the new cookie; the requested id is updated.

| Cookie
| Built from `SessionCookieConfig` (name, path, domain, `HttpOnly`, `Secure`, `Max-Age`, attributes). On a secure request the cookie is `Secure` unless `setSecure` or `<secure>` was set. For the root context the cookie path is `/`.

| URL rewriting
| `encodeURL`, `encodeRedirectURL` append `;jsessionid=<id>` to application URLs while the client sends no cookie and `URL` is a tracking mode.
|===

== Request identity and connection

`getRequestId()` is unique per request (a JVM-wide counter). `getServletConnection()` reports the protocol, the `isSecure()` flag, and a connection id derived from the socket address pair (`remote-ip:port-local-ip:port`, `?-?` when Chappe gives no address). Two limits come from the Chappe `Request` API, which exposes neither a connection identity nor the HTTP/2 stream id (BUG-20261009-09, open, a Chappe follow-up):

* the connection id is not unique for the lifetime of the JVM: two connections reusing the same ephemeral port get the same id;
* `getProtocolRequestId()` is `""` for HTTP/2 instead of the stream id, and `getProtocolConnectionId()` is `""` on every protocol.

`ServletContext.getVirtualServerName()` returns `vidocq` unless `FoyChappeBoot.Builder.virtualServerName(...)` sets it. `getRealPath(path)` answers the file-system path of a resource held in a directory (canonicalised first), and `null` for a resource inside a jar or a missing one.

== Servlet 6.1 API comparison

[cols="1,1,3",options="header"]
|===
| Area | Foy status | Notes

| Core (`Servlet`, `HttpServlet`, `Filter`)
| ✅
| Near-complete coverage in the official TCK.

| `RequestDispatcher` (forward / include / named / error / async)
| ✅
| Parameter merge, named dispatch of unmapped servlets, nested forward keeping the originals, response closed after a forward. Cross-context (`getContext`) **implemented** via `CrossContextRegistry` (contextPath match on contexts deployed in the same JVM).

| Default servlet, welcome files, `HttpServletMapping`
| ✅
| Static content with conditional GET and ranges, welcome files, `MappingMatch` for every dispatch; see xref:usage.adoc#default-servlet-and-static-content[Usage].

| Web fragments (`web-fragment.xml`)
| ✅
| **Implemented** — discovery, §8.2.2 ordering and §8.2.3 merge; see <<web-xml-and-web-fragment-xml-coverage>>.

| Async (`AsyncContext`)
| ✅
| Cycles, `AsyncListener` events (`onStartAsync`, `onTimeout`, `onError`, `onComplete`), timeout routed to an error dispatch (`500`, error pages applied); see xref:usage.adoc#async-asynccontext[Usage].

| Response streaming and buffering
| ✅
| Commit on buffer overflow, `flushBuffer` and a complete `Content-Length`; live chunked (HTTP/1.1) or DATA-frame (HTTP/2) body through a bounded pipe; `setBufferSize` honoured.

| Non-blocking I/O (`ReadListener`, `WriteListener`)
| ✅
| On async-started requests and upgraded connections. Not resumed after an `AsyncContext.dispatch`; no `ReadListener.onError` on async timeout.

| Response trailers (`setTrailerFields`)
| ✅
| HTTP/1.1 chunked and HTTP/2; supplier called after the body on Chappe's thread; see xref:usage.adoc#response-trailers[Usage] for the limits.

| HTTP Upgrade (`HttpUpgradeHandler`, `WebConnection`)
| ✅
| HTTP/1.1 only; blocking and non-blocking streams; `destroy()` on close, I/O error or undeploy; no idle timeout once upgraded.

| HTTP/2 server push (`PushBuilder`)
| ❌
| Not supported: `newPushBuilder()` returns `null` (deprecated in Servlet 6.1).

| Multipart (`@MultipartConfig`)
| ⚠️
| **Buffered in memory** — no streaming parse, no temp-file spill; limit/threshold handling partial (8 of 14 `PartTests`/`Part1Tests` still fail).

| Sessions
| ✅
| `InMemorySessionStore`; SPI `SessionStore` for distribution; `changeSessionId`, expiry reaper, tracking modes, URL rewriting.

| Security (BASIC, FORM, constraints)
| ✅
| `<security-constraint>`, `@ServletSecurity`, `setServletSecurity`, `deny-uncovered-http-methods`, transport guarantee, `security-role-ref`, `declareRoles`, `login`/`logout`/`authenticate`; see <<security>>.

| Security (CLIENT-CERT, DIGEST, Jakarta Authentication)
| ❌
| CLIENT-CERT deferred, DIGEST not supported (both answer `403` on protected resources); Jakarta Authentication and Authorization not implemented.

| WebSocket (Jakarta WebSocket over the upgrade)
| ❌
| Not implemented (planned, no date); HTTP Upgrade itself is available.

| JSP
| ❌
| Not supported by Foy itself; planned through a JSP-engine SPI plugged by xref:ibarra::index.adoc[Ibarra] (Jakarta Pages 4.0).
|===

== Other CDI containers [.tag-new]#NEW#

Foy does not need Vauban: give `FoyChappeBoot` the `BeanManager` of any CDI 4 container (`CDI.current().getBeanManager()`). Without `foy-cdi-vauban`'s build-time index, Foy finds the web components by walking the container's `Servlet`, `Filter` and `EventListener` beans (foy#18).

* **The request context is active for each request** — Foy activates it through the standard `RequestContextController` before the application's request listeners, and deactivates it after them, on the thread that served the request (an asynchronous request included: Foy waits for it). `@RequestScoped` beans work in servlets, filters and listeners, and the container fires `@Initialized(RequestScoped.class)` and `@Destroyed(RequestScoped.class)`. If the context is already active (an embedding runtime activated it), Foy leaves it alone. Up to {release-version}, Foy activated it under no container, Vauban included (BUG-20261010-01). On Vauban, this needs a Vauban with its built-in `RequestContextController` (link:https://codefloe.com/Vidocq/vauban/issues/147[vauban#147]); before it, the request context was not activated under Vauban and a `@RequestScoped` bean failed with `ContextNotActiveException`.
* [.tag-new]#NEW# **The session context, on Vauban** — `@SessionScoped` beans live in the `HttpSession`: one instance per session, created on first use (which creates the session), destroyed with it when it is invalidated or expires, between `@BeforeDestroyed` and `@Destroyed(SessionScoped.class)`; a new session fires `@Initialized(SessionScoped.class)`. CDI Lite leaves the session context to the servlet container (CDI 4.1 §6.7.2): Vauban's `vauban-webcontexts` provides it, and `foy-cdi-vauban`, which depends on it, drives it from Foy's request and session events (foy#21). Nothing to configure. Passivation is not covered: the instances are not written out with the session.
* **The session context, on another container** — Foy finds the listeners that drive a CDI implementation's contexts through the `io.vidocq.foy.spi.cdi.CdiContextListeners` service, registers them ahead of the application's listeners when it is given that implementation's `BeanManager`, and an adapter such as `foy-cdi-vauban` provides them. Unlike a `ServletContainerInitializer`, such a provider does not make Foy start an application that has no web component. Weld's own servlet integration, `weld-servlet-core`, also runs on Foy: its `ServletContainerInitializer` starts Weld and manages the request and session contexts itself; Foy is then given no `BeanManager`, and servlets declared in `web.xml` reach their beans through `CDI.current()`.

`foy-it-weld`, part of every build and never published, runs Foy on Chappe with Weld SE 6.0 (CDI 4.1) on a class path, without `foy-cdi-vauban`: a servlet, a filter and a listener get an injected bean, a `@RequestScoped` bean is one instance per request, and the request context events fire. No Open Liberty module: on a server, use the server's own Servlet container.

[.tag-new]#NEW# The session scope has its own pair of modules, never published, running the same HTTP scenarios from `foy-it-session-scenarios`: `foy-it-weld-servlet`, the reference, where Weld's servlet integration manages the session context, and `foy-it-vauban-session`, where `vauban-webcontexts` does. Both check one cart per session across requests, two carts for two clients, a new and empty cart after `invalidate()` with the old one's `@PreDestroy` run, and the session events.

== Optional JSP-engine service

`foy-api` exports `io.vidocq.foy.spi.jsp.JspEngine`; Foy core discovers it
with `ServiceLoader`. This SPI uses only Servlet/JDK types. Foy has no Jakarta
Pages dependency and accepts deployments without an engine.

`WebAppDeployer.deploy(model, options, applicationLayer)` opens one engine
application before initializers/listeners. It supplies the `jsp` servlet's
`*.jsp` and `*.jspx` mappings, respecting application mappings, and backs
`ServletContext.addJspFile` and descriptor `jsp-file` declarations.
Engine-owned servlet instances retain application-layer isolation; Foy owns
their initialization and destruction. Stop and drain the HTTP server before
closing the deployment. Engine application close follows servlet and listener
destruction; closing a deployment does not drain requests itself.

`jsp-config` is exposed through immutable standard `JspConfigDescriptor` views.
Ordered fragments contribute property groups; root taglib locations take
precedence over fragments, while conflicting fragment locations fail merging.
Configuration is available before engine startup. Engine applications can expose
constructor-based TLD listener descriptors. Foy deduplicates their classes before
construction, preserves descriptor-declared listeners, and registers remaining
TLD listeners with restricted dynamic configuration during context initialization.
They share the normal listener lifecycle and are destroyed before engine close.
Ibarra provides the optional page-engine implementation and TLD discovery.

== Compatibility

* Java 25 (LTS)
* Maven 3.9.16
* Jakarta Servlet 6.1
* Any CDI 4 container (Vauban, Weld) — see <<other-containers>>
* Strict Java Modules, virtual threads (a Foy VT per request, next to Chappe's connection VT)
