= What's new
:description: Everything that changed in Foy since the {release-version} release — Servlet security enforcement, streamed multipart and request body limits, the CDI request and session contexts, and Foy proven on Weld SE and with Weld's servlet integration.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

== CDI

* **The request context is active for each request** — when `FoyChappeBoot` is given a `BeanManager`, Foy activates the CDI request context around each request, through the standard `RequestContextController`, so `@RequestScoped` beans work in servlets, filters and listeners, and the container fires the request context events. {release-version} activated it under no container, Vauban included: a `@RequestScoped` bean failed with `ContextNotActiveException` (BUG-20261010-01). The session context is not activated. xref:reference.adoc#other-containers[Other CDI containers]. Under Vauban too, since Vauban provides the built-in `RequestContextController` (link:https://codefloe.com/Vidocq/vauban/issues/147[vauban#147]): concurrent requests each get their own request-scoped instances.
* **Proven on Weld SE** — the new `foy-it-weld` module, never published, runs Foy on Chappe with Weld SE 6.0 without `foy-cdi-vauban`: servlets, filters and listeners get injection, request-scoped beans live per request (foy#18). xref:reference.adoc#other-containers[Other CDI containers].
* **`@SessionScoped` on Vauban** — the session context is active for each request: `@SessionScoped` beans live in the `HttpSession` and are destroyed with it, with the `@Initialized`, `@BeforeDestroyed` and `@Destroyed(SessionScoped.class)` events. Vauban's new `vauban-webcontexts` provides the context and `foy-cdi-vauban` drives it; nothing to configure. A session-scoped bean used to fail with `ContextNotActiveException` (foy#21). xref:reference.adoc#other-containers[Other CDI containers].
* **The contexts reach error pages, denials and async threads** — error pages, `onComplete`, security denials and the error pages of refused paths run before `requestDestroyed`, and an `AsyncContext.start()` thread gets the context listeners bound: a `@RequestScoped` or `@SessionScoped` bean used there no longer fails with `ContextNotActiveException` (BUG-20261010-07, BUG-20261010-08, BUG-20261011-07). xref:reference.adoc#other-containers[Other CDI containers].
* **`CdiContextListeners`, a service for the adapters of CDI implementations** — Foy registers the listeners a provider gives for the `BeanManager` it is given, ahead of the application's listeners. xref:reference.adoc#other-containers[Other CDI containers].
* **Weld's servlet integration runs on Foy** — `weld-servlet-core`'s initializer starts Weld, which manages the request and session contexts itself. `foy-it-weld-servlet` uses it as the reference for the session scope, and `foy-it-vauban-session` runs the same scenarios on Vauban. xref:reference.adoc#other-containers[Other CDI containers].

== Boot

* **`FoyChappeBoot.Builder.applicationLayer(ModuleLayer)`** — the layer the JSP engine is looked up in (default `ModuleLayer.boot()`), in named modules and their ancestors only. xref:reference.adoc#optional-jsp-engine-service[JSP-engine service].
* **JSP-only applications are deployed** — `JspEngine.hasPages(ModuleLayer)`, a new default method answering `true`, is asked when the application has no servlet, filter, listener, descriptor content or initializer. `build()` is empty only when there is no engine, or it answers `false`. xref:reference.adoc#optional-jsp-engine-service[JSP-engine service].
* **`FoyChappeBoot.Builder.componentSource(Function<Class<?>, URL>)`** — attributes discovered classes to their real jar, so the exclusions of an absolute ordering and of `metadata-complete`, the application roots and the initializers hold when a harness loads several jars from one class loader (BUG-20261012-01, vidocq#228). xref:usage.adoc#native-layout-descriptors-fragments-and-resources[Native layout].

== Observability

* **`Mounted.activeSessions()` and `Mounted.listenerClassNames()`** — two read-only accessors on `FoyChappeBoot.Mounted` for dev consoles and monitoring, without reading foy-core: the live session count and the registered listeners' class names. xref:reference.adoc[Reference].

== Security

* **The Servlet security model is enforced** — `<security-constraint>` from `web.xml` and its fragments, `@ServletSecurity` and `setServletSecurity` apply per url-pattern before any filter or servlet runs, with `<deny-uncovered-http-methods/>`, the transport guarantee (`403`, or a redirect to `confidentialPort`), `security-role-ref` and `declareRoles`. {release-version} parsed the descriptor constraints without enforcing them. xref:usage.adoc#application-security[Application security].
* **BASIC and FORM login** — `login-config` BASIC (realm `Restricted` by default) and FORM (`j_security_check`, server-side saved target, session id rotation); `login()`, `logout()` and `authenticate()` follow the configured mechanism. CLIENT-CERT is covered below; DIGEST is unsupported and fails closed. xref:reference.adoc#security[Security reference].
* **`IdentityStore` replaces `SecurityProvider` (API break)** — declare users with `FoyChappeBoot.builder().user(...)` (salted SHA-256 in memory) or plug an `IdentityStore`. `SecurityProvider` and `AuthenticatedUser` are removed. xref:migration.adoc#security-behaviour-changes[Migration].
* **TCK** — the `spec.security.*` family passes 59 of its 59 tests (Phase 5 exit: 22). xref:tck.adoc[TCK].

* **CLIENT-CERT authentication** — `login-config` CLIENT-CERT authenticates from the TLS client certificate: `FoyChappeBoot.Builder.certificateUser(subjectDn, roles...)` maps a subject DN (compared strictly, ignoring spacing and case) to application roles, or an `IdentityStore` overrides the new default method `validate(X509Certificate[])`. The principal name is the leaf subject in RFC 1779 form. A missing or unmapped certificate answers `403`. The listener asks for the certificate with chappe's `Server.Builder.tls(SSLContext, ClientAuth)`. xref:usage.adoc#client-cert[Client certificates].
* **The Servlet 6.1 section 3.10 TLS attributes** — `X509Certificate`, `cipher_suite`, `key_size`, `ssl_session_id` and the new `secure_protocol` are seeded on a TLS request, without firing attribute listeners. xref:reference.adoc#request-identity-and-connection[Request identity and connection].

== TCK

* **Every test of the Servlet TCK that runs passes** — 1707 of 1714 tests run, 7 skipped (HTTP/2 server push), 0 errors (CLIENT-CERT exit: 1702). `foy-tck` now runs the JSP pages of the TCK wars with Ibarra (Jakarta Pages 4.0) plugged into Foy's JSP-engine service: it compiles them at deployment and hands Foy the engine and the layer of the compiled pages. The 3 JSP tests of `ServletContext40Tests` and the 2 FORM tests whose error page is a JSP now pass (BUG-20261011-04). Foy itself still does not depend on Ibarra. xref:tck.adoc#jsp-pages[JSP pages].

== Multipart and request bodies

* **Multipart is streamed** — `getParts()` parses the body while it streams in (RFC 7578): a part stays in memory up to `fileSizeThreshold`, then goes to an owner-only temporary file under the multipart `location`, deleted at the end of the request (async cycle included). `maxFileSize` and `maxRequestSize` are enforced while streaming. {release-version} buffered the whole body in memory and ignored the location and the threshold. xref:usage.adoc#file-upload[File upload].
* **`<multipart-config>` and `setMultipartConfig` reach the request**, like `@MultipartConfig`, and a configuration is now required: without one, `getParts()` throws `IllegalStateException`. xref:migration.adoc#request-body-behaviour-changes[Migration].
* **Form fields of a multipart body are request parameters**, with the part, request, `_charset_`, ISO-8859-1 charset order. xref:usage.adoc#file-upload[File upload].
* **An over-cap request body is no longer drained without bound** — chappe bounds the drain it performs after the response with `maxDrainSize` (1 MiB by default), so an endless chunked body is cut off (BUG-20261011-11, fixed by chappe#28).
* **Container request body limits** — `FoyChappeBoot.Builder` gains `maxChunkedRequestBodySize` (10 MiB), `maxFormBodySize` (2 MiB), `maxMultipartParts` (50) and `maxMultipartPartHeaderSize` (8 KiB); an uncaught limit answers `413` on a synchronous dispatch. xref:reference.adoc#request-body-limits[Request body limits].
* **TCK** — `PartTests` and `Part1Tests` pass 14 of 14 (Phase 6 exit: 6); the full suite then passed 1702 of 1714 tests run, 7 skipped (99.3 %), and the API signature test passes. xref:tck.adoc[TCK].
