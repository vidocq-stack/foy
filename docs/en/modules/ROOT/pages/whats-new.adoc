= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* **Jakarta WebSocket 2.2, lot 1** — the programmatic server API in the new optional `foy-websocket` module: `ServerContainer.addEndpoint(ServerEndpointConfig)`, the RFC 6455 handshake, a same-origin policy with the `io.vidocq.foy.websocket.allowed-origins` init parameter, sessions with limits, timeouts and close codes. Annotated endpoints and the client API come in later lots. xref:usage.adoc#websocket[Usage], xref:reference.adoc#websocket-module[reference].
* **WebSocket origin messages name the configured setting** — the init parameter `io.vidocq.foy.websocket.allowed-origins.setting-name` lets a runtime that fills the origins from its own key (Vidocq: `vidocq.websocket.allowed-origins`) have the refusal WARNING and the malformed-entry error name that key. xref:usage.adoc#websocket-origins[Usage], xref:reference.adoc#websocket-module[reference].
* **Takeover SPI** — `io.vidocq.foy.spi.websocket` (`WebSocketUpgradeHandler`, `WebSocketListener`, `WebSocketPeer`) and the `ComponentInstantiator` context attribute let a WebSocket implementation run on Foy without reaching into `foy-core`. xref:reference.adoc#websocket-spi[Reference].
* **`@Inject HttpServletRequest`, `HttpSession` and `ServletContext` on Vauban** — the beans CDI requires of a Servlet container, `@RequestScoped`, `@SessionScoped` and `@ApplicationScoped`, produced by `foy-cdi-vauban` with client proxies generated at its build; the application declares nothing. They work wherever the request context does, `AsyncListener` callbacks and `AsyncContext.start` tasks included. An application's own producer of one of these types now makes an ambiguous dependency. xref:usage.adoc#servlet-built-in-beans[Usage], xref:internals.adoc#servlet-built-in-beans[Internals], xref:migration.adoc#servlet-built-in-beans[Behaviour changes].
* **`FoyChappeBoot.Builder.initParameter`** — sets a servlet-context init parameter from code. xref:reference.adoc#foychappeboot[Reference].
* **Fix: dynamic filter mappings honour `isMatchAfter`** (BUG-20261114-01). xref:migration.adoc[Behaviour changes].
* **Undeploy in order** (BUG-20261114-08, BUG-20261115-01 to -06) — closing a deployment refuses new requests and WebSocket handshakes with `503 Service Unavailable` and `Retry-After: 3` (the undeploy's bound, in seconds), never with an error page of the application; it closes the upgraded connections (a WebSocket peer gets its 1001 Close; one that does not read, while a send to it holds that Close past 2 s, has its connection cut, and the blocked send fails with an `IOException`), lets the requests in service finish for up to 2 s, refuses cross-context dispatches into the application, then destroys it. Close the deployment before you stop the server. xref:migration.adoc[Behaviour changes], xref:reference.adoc#foychappeboot[`Mounted.close()`].
* **`getContext` follows one rule for every caller** (BUG-20261115-07) — the longest context path the URI lies under, on a segment boundary, wins, and the root application holds every URI no other application does (section 4.8): another application is now found by a URI below its path (`getContext("/b/x")`), and, when a root application is deployed, a URI no other application holds returns the root application. During its undeploy an application still finds itself. xref:migration.adoc[Behaviour changes].
* **A WebSocket close the container initiates reaches `onClose` as 1006** (BUG-20261115-08, Jakarta WebSocket 2.2 section 2.1.5) — the undeploy, the idle and send timeouts, a message over the limit, a failed `onOpen`, a protocol violation of the peer and an `Error` from a message handler give `Endpoint.onClose` 1006 with a reason naming the cause, while the peer still reads the Close frame's own code (1001, 1009, 1011, ...). A close of the peer keeps the peer's code, a `Session.close(...)` of the application its own. xref:usage.adoc#websocket-close-codes[Close codes], xref:migration.adoc[Behaviour changes].
* **A WebSocket close crossed by the peer's Close hears the Close that went out first** (BUG-20261115-08) — when a Close of the peer, or the undeploy's, goes out just before a close of the session (`Session.close(...)`, a timeout, a message over the limit, a failed `onOpen`) or of the undeploy, `Endpoint.onClose` hears that first Close, no longer this side's own reason, as Jakarta WebSocket 2.2 section 2.1.5 asks. `WebSocketPeer.close` of the takeover SPI returns whether the call sent the Close frame, from Chappe's `WebSocket.sendClose`, a new method (`close` is unchanged): this Foy needs a Chappe of the same line. xref:usage.adoc#websocket-close-codes[Close codes], xref:reference.adoc#websocket-spi[reference], xref:internals.adoc#websocket-takeover[Internals].
* **An `Error` from a WebSocket listener's `onClose` is logged, never thrown into Chappe's thread** (BUG-20261116-01) — whichever thread delivers `onClose`, the takeover logs what the listener throws once at WARNING and still calls `destroy()`; an `Error` from `onOpen` reaches Chappe as an `IOException` carrying it. xref:internals.adoc#websocket-takeover[Internals].
* **HTTP sessions survive a dev swap** — `Mounted.closeExportingSessions()` undeploys like `close()` but exports the live sessions, and `Mounted.importSessions(byte[])` imports them into the next deployment before it is mounted: same `JSESSIONID`, same attributes, no `sessionCreated` or `sessionDestroyed`. A session whose attributes cannot all be written or read stays behind whole; a CDI adapter binds its container through the new `CdiContextListeners.aroundSessionImport` default method. CDI state does not move yet: until Vauban writes its session-scoped beans and client proxies, a session that holds a `@SessionScoped` instance (an `@Inject HttpSession` included) or a CDI client proxy stays behind. xref:internals.adoc#sessions-across-redeploy[Internals], xref:reference.adoc#foychappeboot[`Mounted`].
