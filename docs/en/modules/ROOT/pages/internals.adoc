= Internals
:description: Request sequence, threading model, container lifecycle, Vauban integration.

[.lead]
This page documents the implementation: what happens between the moment an HTTP connection lands on Chappe and the moment a Servlet writes its response. It complements xref:concepts.adoc[Concepts] (vocabulary) and xref:reference.adoc[Reference] (API).

[#generated-code]
== Generated code and reflective fallback

Every brick of the suite documents, in a section of this name, what it generates, who generates it and when, what
looks it up at run time, and what runs instead when it is missing. For Foy that is the description and the factory
of each Servlet, Filter and listener, and the class index initializers ask about; reading the class file, then
reflection, stay as the fallback tiers, unchanged (<<_component_resolution_tiers>>).

[cols="2,2,3,3"]
|===
| Generated | By, and when | Used at run time by | Without it

| `X$$FoyComponent`, a `WebComponent`: the component's annotations as a descriptor, and a factory that calls its
  constructor
| `foy-processor` in javac, with its `META-INF/services` entry; on Vidocq the
  `vidocq-runtime-foy-servlet-extension-codegen` bundle puts it on the processor path, and `vidocq:generate` runs it
  over the dependency jars that hold web components, fragments or initializers
| `WebComponentRegistry` at deployment: the `ServiceLoader` of `WebComponent`, then `X$$FoyComponent` by name
| The `CLASS_FILE` tier decodes the annotations from the class bytes and defines a hidden factory class; when it
  cannot, the `REFLECTION` tier. Both need the package opened to `io.vidocq.foy.core` in a named module.

| `META-INF/foy/class-index.list`, the binary names of the compiled classes
| `foy-processor`
| `IndexedHandlesTypesResolver`, to answer the `@HandlesTypes` of a `ServletContainerInitializer` without a scan
| `ClassFileHandlesTypesScanner` reads the class bytes of the jar or directory.

| The web components CDI resolves (`CdiWebComponents`)
| `FoyWebExtension`, the Build Compatible Extension of `foy-cdi-vauban`, which Vauban runs in javac
| `CdiWebComponentsCreator`, which loads the recorded class names without initialising them
| The extension runs at boot.
|===

=== When the fallback runs

* A component compiled without `foy-processor`, in a jar of another build that `vidocq:generate` did not enrich.
* A companion found by name in a named module whose package neither `provides` it nor exports it.

=== Which path ran

* One `INFO` line per class resolved through the `CLASS_FILE` tier
  (`foy: <class> resolved through the Class-File tier (not processed at build time)`), one `WARNING` per class on the
  `REFLECTION` tier, naming the reason; nothing per request.
* The `NO_REFLECTION` architecture rule of `foy-architecture-tests` fails Foy's own build on any reflection outside
  the tiers.

=== WebSocket takeover

A WebSocket handshake is an ordinary request until the end of the filter chain: the `foy-websocket` filter (on `/*`, after the application's filters) validates the handshake, negotiates the sub-protocol, runs `modifyHandshake` and `getEndpointInstance` on the request thread, then calls `HttpServletRequest.upgrade` with a `WebSocketUpgradeHandler` (`io.vidocq.foy.spi.websocket`). The bridge hands that handler to Chappe's WebSocket upgrade instead of a raw connection: Chappe writes the `101` and runs the frames, and delivers events to the handler's `WebSocketListener`. `foy-websocket` never touches `chappe-api`; the SPI is the only seam.

An undeploy refuses new requests (503) and leaves the cross-context registry, then closes the upgraded connections, waits for the requests in service, destroys the filters and servlets, invalidates the sessions and fires `contextDestroyed`: the upgraded connections close before any of the application goes, so their handlers end while it is intact. It closes them all at once, each on a virtual thread of its own, and waits for them until one deadline, 3 s after the start of the undeploy (`VidocqServletContext.UPGRADED_CONNECTIONS_GRACE`): connections that each wait for their peer cost the undeploy that much in all, and an `Error` from one handler's `onClose` or `destroy()` is logged without stopping the others or the rest of the undeploy. For a WebSocket, the bridge sends the 1001 Close, then delivers `onClose` and calls `destroy()` without waiting for the peer's answer: on that thread, or, when an event in progress returns after the Close went out, on the connection's thread as soon as it returns, under the lock every event takes, and the undeploy waits for that `onClose`. `onClose` never comes before the Close frame, except when the Close is held past the deadline below: the connection is then cut without one. No frame read once the undeploy closed the connection reaches the listener. Chappe sends the Close under the connection's write lock, which it takes with no time limit and which a send blocked on a peer that does not read holds: the bridge sends the Close on a virtual thread of its own and stops waiting for it at the deadline. A Close still held then never goes out: the bridge cuts the connection (Chappe's `WebSocket.abort()`, CHAPPE-060, which closes the socket without the write lock), so the blocked send fails with an `IOException` saying the connection was cut (the takeover's peer wraps Chappe's failure), the Close's thread returns, and the event that made the send gets 500 ms more (`WebSocketTakeover.CUT_GRACE`) to return, so the takeover still ends with its 1001 before the undeploy goes on; the read the cut ends reaches no `onError`, and an `onOpen` that rethrows the `IOException` of a send the cut ended reaches no `onError` either and ends with that 1001, not 1011. Any other failure of `onOpen` during the undeploy ends as it does outside one, with `onError` then 1011, except an `IOException` once the undeploy closed the connection: like every I/O failure from then on, it reaches no `onError` (BUG-20261114-07), and the connection still ends with 1011. The hook leaves the end of a failed `onOpen` to Chappe's `onError`, which always follows it on the connection's thread, and waits for that end with no deadline of its own, within the context's 3 s, as it waits for an `onClose` already running, whether that `onError` takes the lock every event takes before the hook or after it. The Close, the wait for the event in progress and the wait for a closing handshake already under way share one 2 s deadline: past it, the connection ends on Chappe's thread after `contextDestroyed`, with a WARNING: once the event in progress returns, or, after an `onOpen`, at the next frame or at the peer's answer to the Close. An `onClose` already running on the connection's thread at the deadline is waited for, within the context's 3 s.

== Dispatch pipeline

For one request, `ChappeServletBridge` runs these steps in order (Servlet 6.1 §3.5.2, §10.10, §12.2):

. *Canonical path.* The context path is stripped on a segment boundary (404 outside the context), then `RequestPaths.canonicalize` removes path parameters, decodes once and normalises; a refused path is a 400 before anything else. The `;jsessionid=` parameter is extracted first for the session lookup. The result drives every decision below; `getRequestURI` stays raw.
. *Mapping.* `ServletDispatcher.find` picks the servlet: exact, then longest prefix, then extension, then the application `/` servlet, then the container default servlet `foy.default`, which the deployer adds (as a non-application mapping) only when `/` is free.
. *Welcome files.* Only when the container default servlet matched: a directory without trailing slash is redirected (302, `Location` from the re-encoded canonical path), a directory path ending with `/` is replaced by the first welcome file that a static resource or a servlet serves, and the mapping is looked up again.
. *Security.* `WebSecurity.admit` applies the constraints of the original canonical path and, when a welcome file replaced it, of the welcome target too; see <<security-enforcement>>.
. *Filter chain.* `FilterRegistry.chainFor(path, dispatcherType, servletName)` collects the filters whose URL pattern matches, then those mapped by servlet name (a filter matching both runs once), each in registration order, filtered by the dispatcher type.
. *Servlet.* The servlet (or the default servlet) runs; a forward, include, async or error dispatch goes through `RequestDispatcherImpl` and `DispatchResolver`, which produce a `DispatchTarget` (servlet, mapping, paths) and rebuild a chain for that dispatcher type with the same URL-then-name rule. Named dispatch looks the servlet up in an index of every registration, mapped or not.
. *Error.* An exception or `sendError` goes to `ErrorPageRegistry` (class hierarchy, then `ServletException` root cause, then status code); a committed response is never replaced, the exception is logged instead.

The session is touched in step 1 (`accessRequestedSession`) for every request carrying a session id, not only when the servlet calls `getSession`, so a busy session does not expire and `getLastAccessedTime()` stays correct.

Body path: `ServletOutputStreamImpl` buffers up to `getBufferSize()` bytes; the commit hands Chappe a `Body` whose reader is a bounded `ResponsePipe`, which the servlet then fills (coalesced writes pushed when the buffer fills, on a flush, at the end). The `ServletInputStream` reads from the Chappe body directly in blocking mode; with a `ReadListener`, a body pump (one virtual thread) reads ahead into a small buffer and drives the callbacks.

[#security-enforcement]
== Security enforcement

Package `io.vidocq.foy.internal.security`.

*At deploy.* `WebAppDeployer` compiles a `ConstraintTable` once: the descriptor constraints first, then each servlet's `ServletSecurityElement` (annotation or `setServletSecurity`) on its url-patterns, except the patterns a descriptor constraint names exactly. Without `<deny-uncovered-http-methods/>`, the uncovered methods are reported then (`WARNING`). `WebSecurity.authenticatorFor(login-config, store)` picks the mechanism: `BasicAuthenticator`, `FormAuthenticator`, or a `DenyingAuthenticator` for any other `auth-method`. A `RoleMapping` holds the declared roles and each servlet's `security-role-ref`s. The three, with the embedder's `SecuritySettings` (identity store, HTTPS port, rotation), form the context's `WebSecurity`.

*At request time.* `WebSecurity.admit(req, res, canonicalPath)` runs for the original REQUEST dispatch only; forward, include, error and async dispatches are not checked again (section 13.8). In order:

. restore the identity cached in the session (FORM);
. decide the constraint of the path and method; when it requires a confidential transport and the request is not secure, answer `403`, or `302` to `https://<Host>:<confidentialPort><uri>` when a port is configured and the Host header is a plain host name and the URI and query are printable ASCII;
. handle a FORM login action (`POST .../j_security_check`): it runs after the transport check, so a confidential application never accepts a password over plain HTTP;
. an excluded method answers `403`;
. an unchecked method proceeds;
. without an identity, the mechanism authenticates the request (the BASIC header), else challenges (`401`, or the forward to the login page);
. an identity without an allowed role gets `403`.

`ChappeServletBridge` calls `admit` on its three branches: the normal one (on the original path, then on the welcome target it resolved to), the directory redirect of the default servlet, and the unmapped path. A refusal goes through the `<error-page>` handling, as `sendError` does.

*Session notes.* The FORM identity and saved target are kept as `HttpSessionImpl` notes, not attributes: no listener, no `getAttributeNames`, out of the application's reach. Notes survive `changeSessionId` and are dropped on invalidation.

*Executing servlet.* `HttpServletRequestImpl.enterServlet(name)` and `leaveServlet(previous)` bracket each servlet invocation, so `isUserInRole` resolves the `security-role-ref`s of the servlet that is executing, through forwards and includes.

*Fail closed.* A context built outside `WebAppDeployer` gets `WebSecurity.UNCONFIGURED`, which refuses every request with `403`; permit-all is only ever chosen explicitly (tests). An exception thrown while checking a request fails closed (the target never runs, `500`). An identity store that throws or returns `null` counts as a refusal. An unsupported `auth-method` and a FORM `login-config` without a login page answer `403` on protected resources.

*Password handling.* The `char[]` handed to the identity store is wiped once it returns. The FORM password, though, also exists as the `String` `j_password` in the request parameter map, which Foy cannot wipe.

== Threading model

* **Two virtual threads per request.** Chappe runs each connection (or HTTP/2 stream) on its own VT and calls the bridge there. The bridge starts the servlet pipeline on a second VT, `foy-request-<n>`, and parks Chappe's thread until the response head is known (the first commit, or the end of a request that never committed). Chappe then writes the head and reads the live body while the servlet keeps writing.
* **Context class loader.** Application code runs with the application's class loader (the one given to `DeployOptions.defaults(loader)` or `FoyChappeBoot.Builder.classLoader`) as context class loader, installed and restored by `ContextLoaderScope`: deployment and undeployment (initializers, context listeners, `init`, `destroy`), the pipeline thread, every `AsyncContext.start` thread, the `ReadListener`/`WriteListener` callbacks, `HttpUpgradeHandler.init`/`destroy` and the session reaper. A cross-context forward, include or async dispatch runs with the target context's loader, and the caller's comes back when it returns; the async cycles, `AsyncListener` events and upgrade handler the target opens keep the target's loader after the dispatch returned. Each `ReadListener` or `WriteListener` keeps the loader of the context that registered it, whatever async cycle the request is in when its callbacks run. Without an application loader, the inherited loader is left untouched (BUG-20261022-06).
* **Context crossing.** Chappe's `RequestContext.CURRENT` (a `ScopedValue`) is re-bound on the pipeline thread. Any other `ThreadLocal` or `ScopedValue` a Chappe filter set on the connection thread is *not* visible to servlet code.
* **No platform pool.** No `ExecutorService` to size; every thread Foy starts (pipeline, `AsyncContext.start`, `ReadListener` body pump, `WriteListener` drain, upgraded-connection pumps, session reaper, async timeouts) is virtual.
* **Async.** `request.startAsync()` lets `service()` return; the pipeline thread waits for the end of the cycle (complete, dispatch, timeout, error), runs dispatches and listeners, then ends the body. The container reserves no platform thread.
* **Trailer supplier.** `setTrailerFields` suppliers are called by Chappe, on its connection thread, after the last byte of the body: request-scoped state is not available there.
* **HTTP Upgrade.** After the `101` head, Chappe passes the raw connection to Foy; `HttpUpgradeHandler.init` runs on Chappe's connection thread (with the application class loader), and the `WebConnection` listener callbacks run on Foy virtual threads, serialised, never before `init` returns.
* **WebSocket.** Each session runs one event at a time (`onOpen`, message handlers, `onClose`, `onError`) on a virtual thread, with the application class loader as context class loader. A session has one asynchronous-send drainer virtual thread, started on demand, and one timer virtual thread when it has an idle or send timeout. A per-handshake context is a `ScopedValue`; the module uses no `ThreadLocal`.

[NOTE]
====
The bridge never `pin`s a VT on a Java monitor — every critical section uses `ReentrantLock` or lock-free structures. No benchmark numbers have been recorded yet — a `BENCH.md` will be created with the first measured run (workspace convention).
====

== Container lifecycle

The deployment lifecycle lives in `foy-core` (`io.vidocq.foy.internal.boot`), not in the transport or the TCK harness:

. `WebAppModel` describes the web application: servlets, filters, listeners, `web.xml` data and options such as `metadata-complete`.
. `DescriptorMerger` merges the parsed `web.xml` with the annotated components (Servlet 6.1 §8.2.3: the descriptor wins on a same-name conflict, `metadata-complete="true"` ignores annotations).
. `WebAppDeployer.deploy(model, DeployOptions)` runs the lifecycle — listeners, `ServletContainerInitializer`s, dynamic registrations, `load-on-startup` initialisation in order — and returns a `Deployment`. A servlet whose `init()` throws (a `ServletException` or a runtime exception) answers 500 and the rest of the application keeps serving; a filter whose `init()` throws is left out of the chain. When the deployment itself fails (an initializer, a `contextInitialized` listener or a component that cannot be instantiated), what was already set up is torn down before the exception propagates.
. `Deployment` exposes `handler()` (the Chappe `Handler`), `servletContext()` and `close()`. `close()` first makes the context refuse requests: from then on the bridge answers 503 before any listener, filter or servlet (`VidocqServletContext.enterRequest`, which also counts the requests in service, asynchronous processing included), with `Retry-After` set to `VidocqServletContext.UNDEPLOY_RETRY_AFTER_SECONDS` (the undeploy's bound, `UNDEPLOY_BOUND`, the later of the two graces below, rounded up to whole seconds: 3 s, by which the undeploy reached `destroy()`) and a plain-text body of its own: no error page of the application runs, since none of its filters or servlets may see a new request. It also takes it out of the cross-context registry: another application's `getContext` no longer finds it and gets, among the contexts that remain, the one that holds the URI (one deployed under a longer path inside it, the root one, or none; its own still resolves a URI under its path to itself, BUG-20261115-07), and the bridge's `invoke` treats a dispatch from another application as a request, refused with a temporary `UnavailableException` once the undeploy began and counted in service otherwise. It then closes the upgraded connections, waits for the requests in service until 2 s after the start of `close()` (`awaitRequestsInService`, Servlet 6.1 §2.3.4: "a server-defined time limit"; Tomcat's `unloadDelay` is 2 s too). Both graces count from the start of `close()`, since the requests keep running while the connections close: the undeploy reaches `destroy()` 3 s after it began at most, destroys filters and servlets, fires `contextDestroyed` and removes the context temp directory (`jakarta.servlet.context.tempdir`).

== Discovery and deployment pipeline

`FoyChappeBoot.Builder.build()` runs these stages in order:

. *Discovery*: `ApplicationSources` walks `ClassLoader.getResources("META-INF/web-fragment.xml")` and the `ServletContainerInitializer` `ServiceLoader`. Each fragment, initializer and annotated class is attributed to its root through `Fragment.sourceKey` (the jar file or the directory), so a jar found twice counts once. A class is attributed through the builder's `componentSource` (default: its code source), for the absolute-ordering and `metadata-complete` exclusions, the application roots and the initializers. The `META-INF` resources are not encapsulated by Java Modules, which makes the class-loader lookup valid on the module path.
. *Ordering*: `FragmentOrderer` applies §8.2.2, absolute or relative, with `<others/>` meaning the fragments not named by the declaring fragment; cycles and duplicate fragment names fail the deployment. `ApplicationSources.ordering` derives from it the roots whose initializers are retained (§8.2.4).
. *Fragment merge*: `FragmentMerger` folds the ordered fragments into the `web.xml` data (`web.xml` wins, conflicts between fragments fail, `url-pattern` clashes fail).
. *Engine lookup*: `WebAppDeployer.jspEngine(ModuleLayer)` finds the JSP engine in the application layer (named modules and ancestors; two engines fail). When nothing else is to be deployed, the engine's `hasPages` decides between a JSP-only deployment and an empty result.
. *Annotation merge*: `DescriptorMerger` merges the annotated components (the ones of excluded or `metadata-complete` roots are dropped) into the result.
. *Deploy*: `WebAppDeployer` runs listeners, then the retained initializers (each with its `@HandlesTypes` classes, resolved from the generated class index with a Class-File scan fallback that reads runtime-retained annotations on types and members), dynamic registrations and `load-on-startup`.

The `async-supported` flag of the chain is recomputed on forward, include, async and error dispatch. The TCK harness takes the same route: it builds fragments from `WEB-INF/lib` and deploys through the product merge.

== CDI integration through Vauban

`foy-cdi-vauban` is deliberately minimal: its single class, `FoyVaubanBootstrap`, returns the current `VaubanContainer`'s `BeanManager`, which the caller passes to `FoyChappeBoot`. `WebAppDiscovery` then resolves the Servlet/Filter/Listener instances through that `BeanManager`, so they can `@Inject` application beans (build-time resolution through Vauban). The component classes come first from the `CdiWebComponents` index beans that `FoyWebExtension` registers, one per archive built with `foy-cdi-vauban` on the processor path; the `Servlet`, `Filter` and `EventListener` beans are walked as well, and a web-annotated bean missing from every index (an archive built without `foy-cdi-vauban`) is still discovered, after the indexed classes, with one `WARNING` naming the class. Without any index (a CDI container other than Vauban), the walk is the only source and one `INFO` line says so.

[IMPORTANT]
====
There are **no CDI producers** for `ServletContext`, `HttpServletRequest` or `HttpSession` yet — `@Inject HttpServletRequest` does **not** work. Scoped Servlet-object beans are a later milestone.
====

== Component resolution tiers

At deployment, `WebComponentRegistry` (`io.vidocq.foy.internal.gen`) resolves every Servlet, Filter and listener class to a `WebComponent` (descriptor plus factory) through four tiers, tried in order:

[cols="1,1,3",options="header"]
|===
| Tier | Source | Behaviour

| `SERVICE_LOADER`
| `META-INF/services/io.vidocq.foy.spi.gen.WebComponent` (or `provides` in `module-info.java`)
| Providers written by `foy-processor`.

| `GENERATED_CLASS`
| `X$$FoyComponent` next to `X`
| The generated companion, found by name (through `publicLookup`) when the service entry is missing. In a named module, declare `provides io.vidocq.foy.spi.gen.WebComponent with ...` (no export needed) or export the package; otherwise resolution falls to the Class-File tier, which needs `opens`.

| `CLASS_FILE`
| Class bytes of `X`
| Annotations decoded with `java.lang.classfile`; the factory is a hidden class defined in `foy-core`'s lookup that carries the constructor `MethodHandle` as class data.

| `REFLECTION`
| `java.lang.reflect`
| Last resort, only when the hidden class cannot be defined. Like the Class-File tier, it needs `opens <package> to io.vidocq.foy.core` for a component in a named module.
|===

The guard test `NoProductReflectionTest` scans the main sources of `foy-core` for three patterns, `getAnnotation(`, `getDeclaredConstructor(` and `Class.forName(`, and fails on any match outside an allow-list of three files:

* `WebComponentRegistry` — the tiers themselves (loading a class by name, the generated companion, the reflective tier);
* `ComponentFactory` — its `Reflective` factory, used only on explicit opt-out and in tests;
* `IndexedHandlesTypesResolver` — loads the `META-INF/foy/class-index.list` entries with `Class.forName(name, false, loader)`, without initialising them.

The guard covers `foy-core` only: `foy-cdi-vauban`'s `CdiWebComponentsCreator` also loads the class names recorded at build time with `Class.forName(name, false, loader)` (no initialisation, no reflective instantiation).

The architecture rule `NO_REFLECTION` of `foy-architecture-tests` checks the bytecode of every shipped module against the same allow-list, `CdiWebComponentsCreator` included: a lookup by name, a member or an annotation read reflectively, or a `java.lang.reflect` type, anywhere else fails the build.

*Logging policy.* One `INFO` line per class resolved through the Class-File tier, one `WARNING` per class on the reflective tier (naming the reason), and nothing per request.

*Class index.* `foy-processor` writes `META-INF/foy/class-index.list` (binary class names). `IndexedHandlesTypesResolver` uses it to answer `@HandlesTypes` of a `ServletContainerInitializer` without scanning; it yields nothing when no indexed class matches. A jar or directory without that index is scanned from its class bytes instead (`ClassFileHandlesTypesScanner`). Its roots are the application roots, the ordered fragments' jars and the initializers' roots. A root is scanned when it is a `file:` jar or directory, or, in an image built by `jlink`, a module's `jrt:/<module>` root. Other locations (remote or nested archives) are not scanned.

*When `opens` is needed.* The Class-File tier defines its hidden class through `privateLookupIn`, so a component of a named application module needs `opens <package> to io.vidocq.foy.core` for the Class-File and the reflective tiers. Companions generated by `foy-processor` (the `SERVICE_LOADER` and `GENERATED_CLASS` tiers) do not need it, and code on the class path (unnamed module) needs nothing.

== Implementation choices

[cols="1,3"]
|===
| Choice | Justification

| No runtime classpath scan
| All `@WebServlet` / `@WebFilter` / `@WebListener` are known at compile time through Vauban. Startup is O(1) in the number of beans, not O(N) in the classpath.

| No runtime reflection on the nominal path
| Aligns with the Vidocq ecosystem's principles. AOT-friendly (GraalVM, Leyden CDS). Reflection remains only as the last, logged tier of the registry.

| Bounded pipe instead of a whole-body buffer
| A committed body goes through `ResponsePipe` (a ring buffer of at least 8 KiB): memory per response stays bounded whatever the body size, and a slow client back-pressures the writing servlet. A response that fits in the buffer is never piped.

| `requires io.vidocq.chappe.api` in `foy-core`
| Temporary M1 coupling — to be replaced in M2 by a `FoyHttpExchange` SPI inside `foy-api`, opening the door to other transports.

| `META-INF/services` only for generated components
| `WebComponent` providers written by `foy-processor` are loaded with `ServiceLoader`; `ServletContainerInitializer`s are also loaded with `ServiceLoader` at boot (`ApplicationSources`), restricted to the roots the fragment ordering retains. Components themselves go through the generated index or the Vauban `BeanManager`.
|===

== Request body ownership

A request body has exactly one owner, decided by the first reader: the application (`getInputStream()` or `getReader()`) or the container (the form parameters, or the multipart parts). The other side then gets an empty stream (the application) or an `IllegalStateException` (`getParts()` after the application took the body).

* *The tracked stream.* Whoever owns it, the body is read through one `ServletInputStreamImpl` held as the request's tracked body, so trailer readiness (`isTrailerFieldsReady()`) and keep-alive follow the bytes actually read, by the application or by the container.
* *`bodySource()`.* The tracked stream wraps Chappe's body stream. A body that declares no `Content-Length` is wrapped in a `BoundedInputStream` capped at `maxChunkedRequestBodySize` (10 MiB by default), which fails with `RequestBodyTooLargeException`; Chappe bounds `Content-Length` bodies itself (`maxRequestSize`).
* *Parameters settled before the body read.* The parameter map is built locally, the query string first and then the body, and published once complete: a concurrent reader never sees a half-built map. A form body above `maxFormBodySize` is refused before any byte is read when its `Content-Length` says so, and while it streams otherwise.
* *Failures.* A failed multipart parse is cached and rethrown as is by every later `getParts()`: the body is never read twice. A failed body read for the parameters propagates once; later `getParameter*` calls see the query-string parameters only.
* *Encoding lock.* Once a body was parsed into parameters or parts, or handed to the application, `setCharacterEncoding` is a no-op (section 3.12).
* *The servlet scope.* Read before any servlet runs (a request listener, a FORM login check), a multipart POST gives the query-string parameters without caching them, so the servlet later sees its fields. An async cycle stays in the scope of the servlet that started it (`asyncServletName`), so a `requestDestroyed` listener at the end of an async request counts as in scope.

== Multipart

* *Delimiter scan.* `MultipartParser` reads the body through a window and finds each `CRLF--boundary` delimiter in linear time (Knuth-Morris-Pratt), so a file that holds near-matches of the boundary costs no backtracking. Boundaries are at most 70 characters (RFC 2046); every line ends with CRLF, a bare LF is malformed. `maxRequestSize`, `maxFileSize`, the part count and the part header size are checked while streaming.
* *`PartSink` and `PartStorage`.* Each part's content goes to a `PartSink`, in memory up to `fileSizeThreshold`, then into a temporary file created by the request's `PartStorage`: random `foy-part-*.tmp` names, owner-only permissions (0600) where the file system is POSIX, under the resolved `location`. A sink that does not finish deletes its file; `PartStorage.close()` deletes every file it still owns, and `Part.write` disowns the file it moves.
* *Configuration.* The multipart configuration of each servlet is frozen with the registrations at `markInitialized`. A request resolves it for the servlet executing on the calling thread, recorded by `enterServlet` on each dispatch, so a forward to another servlet changes it. The annotations of a class given to `addServlet(Class)` (`@MultipartConfig`, `@ServletSecurity`) are read even under `metadata-complete`, deliberately: the application registered that class programmatically.
* *Epilogue.* After a successful parse the tracked body is read to its end, within the same caps, so a chunked body's trailers are ready.
* *Cleanup.* `releaseParts()` runs in the `finally` of `ChappeServletBridge.runPipeline`, after the whole request including its async cycle: the temporary files go with the request, and a `getParts()` after it throws `IllegalStateException`.

== Known limits

* `WEB-INF/lib` nested jars of a WAR are not opened; see xref:tck.adoc[].
* HTTP/2 server push is not supported (`newPushBuilder()` returns `null`): push is deprecated in Servlet 6.1 and Chappe sends no `PUSH_PROMISE`. See xref:usage.adoc#http2-server-push[HTTP/2 server push].
* Response trailers: the supplier runs on Chappe's thread after `service()` (no request-scoped state); on HTTP/1.1 a `Content-Length` set after `setTrailerFields`, or a `Connection: close` response, drops the trailers silently; `reset()` keeps the supplier.
* Non-blocking I/O: `ReadListener.onError` is not called on an async timeout; a `WriteListener` is not resumed after an `AsyncContext.dispatch`; bytes still waiting at the end of a cycle are sent in blocking mode, bounded only by Chappe's write timeout for a client that never reads (BUG-20261010-03).
* HTTP Upgrade: no idle timeout once upgraded — a handler that never reads nor closes keeps the connection until a write fails or the application is undeployed. HTTP/1.1 only.
* A request whose `ReadListener` is still waiting for upload bytes when the request ends (a client gone silent mid-body) is answered first, then its connection is closed instead of being kept alive.
* Cross-context dispatch (`ServletContext.getContext`): **implemented** via `CrossContextRegistry`, on the contexts deployed in the same JVM. One rule whoever asks (section 4.8, as in Tomcat and Jetty): the URI resolves to the context whose path is the longest one it lies under, on a segment boundary (`/app` holds `/app` and `/app/x`, not `/application`), and the root context holds every URI no other context does. The one exception is the undeploy: the application has left the registry, so the other applications no longer find it (BUG-20261115-04), yet it still counts as deployed for its own lookups (BUG-20261115-07).
* Multipart: the body parameters of a multipart request are decided by the servlet executing when the parameters are first read; the epilogue after the closing delimiter is read by Foy within the caps, and what a client sends after the response is drained by Chappe, which bounds that drain (`maxDrainSize`, 1 MiB by default); no aggregate in-memory cap on the stored parts beyond the body size (each part stays under `fileSizeThreshold` in memory, the parts together under the body cap); reading the parameters reads the form fields (parts without a file name) whole into memory, so their total size is checked against `maxFormBodySize` first.
* Jakarta WebSocket: lot 1 (programmatic server API) only; annotated endpoints and the client API are not implemented yet. In lot 1:
** the handshake is HTTP/1.1 only (no WebSocket over HTTP/2, RFC 8441);
** Chappe reassembles a message up to its own 64 MiB cap before Foy applies the session's limit (64 KiB by default), so an oversize message is read whole before the 1009;
** no CDI request or session context is active in an endpoint callback;
** invalidating the `HttpSession` of the handshake does not close the WebSocket with 1008.
* JSP: not supported by Foy itself; a page engine such as Ibarra (Jakarta Pages 4.0) plugs into the JSP-engine service (xref:reference.adoc#jsp-engine[Optional JSP-engine service]).
* Security: DIGEST is not supported (it fails closed with `403`); security constraints match url-patterns case-sensitively, and a resource is served only under its exact real name, so a request that differs in case gets 404 on macOS and Windows (BUG-20261011-05). On a Linux case-insensitive mount (ext4 casefold, vfat/exFAT, CIFS) `toRealPath` returns the requested spelling and the folding goes undetected (BUG-20261013-01); serve static resources from jars or from a case-sensitive file system there.

No comparative numbers (Tomcat, Jetty) have been recorded yet — a `BENCH.md` will be created with the first measured run (workspace convention).
